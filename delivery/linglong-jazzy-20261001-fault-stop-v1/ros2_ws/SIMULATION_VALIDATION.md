# 模拟验证与性能基线

已执行结果见 [2026-09-25 基线](SIMULATION_BASELINE_20260925.md)，包含实际指标、环境和原始证据路径。

这套验证直接编译生产代码所用的 `sim_core.hpp`，测试四关节位置模拟核心。测试入口在 `tools/run_sim_validation.sh`，C++ 驱动为 `src/linglong_control/test/sim_validation.cpp`，报告驱动为 `tools/run_sim_validation.py`。

它没有运行 ROS2、controller_manager、DDS、EtherCAT 或真实伺服。结果用于验证控制核心逻辑和当前 Linux/WSL 主机上的普通调度表现，不能替代 ROS 集成、实机性能或生产验收。

## 一条命令复现

Ubuntu/WSL 安装 C++17 编译器、CMake、make 和 Python3 后，在 `ros2_ws` 目录执行：

```bash
bash tools/run_sim_validation.sh
```

无需 ROS、pytest、网络或硬件。默认先进行 Release 构建和 CTest，再运行完整套件，耗时主要是 6 组各 20 秒的真实计时测试。CPU 负载场景使用两个计算线程，测试结束会停止线程。

结果保存到独立的 `verification/simulation-时间戳/`：

- `manifest.json`：主机、编译器、参数、源码及二进制 SHA256。
- `summary.json` 与 `REPORT.md`：整体结果及每个场景的指标。
- 每个场景的 `.json/.stdout/.stderr`：原始结果和错误。
- 调度场景的 `.csv`：每个周期的计划时间、实际时间、周期间隔、唤醒延迟、执行耗时，单位为微秒。

默认套件共 10 个场景，任何一个不满足判据或采集失败，整体退出码非零。失败场景不会被从汇总中删除。Python 独立复算 CSV 的分位数和时间关系，核对 C++ 汇总结果；空数据、NaN、结果与退出码矛盾不能被视为通过。

## 可靠性：随机故障及锁存

固定三个种子 `20260925/20260926/20260927`；每个种子、每种故障进行 200 次，合计 5400 次。故障发生前先运行轨迹，正常周期时长在 5–15 ms 中随机取值，注入轴和注入前运行周期也随机选择。

九类注入：NaN 指令、Inf 指令、位置越限、目标跳变、跟随误差、周期超时、非法周期、反馈中断、显式模拟故障。

每次必须满足：故障码正确、控制不再 active；连续 20 次读写/激活/配置尝试不能绕过锁存，也不能继续改变模拟位置。反馈超时累计的**模拟失联时间**需达到 100 ms，且最多在下一个随机周期被发现，所以上界为 115 ms。该指标不是 DDS 延迟或物理停机时间。

合格条件：全部故障被正确检测、全部锁存验证通过。5400 次通过只能表明覆盖的注入案例通过，不能据此推断真实设备 MTBF 或统计意义上的可用率。

## 故障恢复：区分两种恢复路径

七类输入/时间异常使用同一个对象执行显式 cleanup → configure → activate，再验证连续 100 个健康轨迹周期。两个持续注入故障先验证故障对象可显式复位，然后重建不含注入源的模拟配置，验证 100 个健康周期；每类结果记录 `recovery_mode`。

这验证的是模拟软件恢复路径，模拟 configure 会重新设置初始状态，并非真实机械臂带载恢复。`max_recovery_cpu_us` 仅是该段测试代码耗时，包含模型初始化和验证循环，不能写成机器人 MTTR。

另外每个种子执行 2000 次停用/激活，合计 6000 次，要求保留当时反馈位置，不能恢复默认零目标。合格条件为零状态转换错误。

## 稳定性：等效 24 小时加速仿真

按 10 ms 的固定虚拟周期执行 864 万次 `read → target update → write`，等效 24 小时控制时间。四轴使用幅度 0.03 rad、频率 0.1 Hz 的连续参考轨迹，模拟器限速 0.1 rad/s。

指标：完成周期数、意外故障数、四轴合并跟踪 RMSE、最大跟踪误差，以及进程峰值 RSS 前后值。跟踪误差按本周期更新后的参考减去 read 得到的反馈计算，包含一个周期的离散延迟；不是电机实际定位精度。

合格条件：全部周期完成、无意外故障、最大误差不超过 0.002 rad。RSS 只作为观察值，峰值不增长不能证明不存在内存泄漏。这不是 24 小时真实驻留运行：虚拟周期会尽可能快地执行。

## 实时性：100 Hz 普通调度的真实计时

使用 steady_clock 和绝对时间 sleep_until，分别测试无额外负载和两个 CPU 计算线程，每种三轮、每轮 20 秒，交替先后顺序。执行超时会跳过错失的时隙，不通过连续补跑掩盖延迟。

分别记录唤醒延迟 P50/P95/P99/max、核心加参考生成执行耗时 P99/max、实际间隔 P99、超过 15 ms 的间隔数、跳过时隙数。

测试前固定的模拟开发门槛：P99 唤醒延迟 ≤ 5 ms；P99 执行耗时 ≤ 2 ms；跳过时隙占比 ≤ 1%；采样数量至少达到计划数量的 90%；不出现核心故障。门槛不是行业标准，也不是最大延迟保证。测试后不因结果失败而放宽阈值。

测试没有配置实时内核、SCHED_FIFO、CPU 隔离或锁页，也没有加入 ROS/DDS/PDO。即使全部通过，也只能描述这次主机和负载条件下的观测分布，不能称为硬实时保证，不能外推到 1 kHz。

## 扩展验证

```bash
# 更长的真实计时窗口：两种负载各三轮、每轮 120 秒
bash tools/run_sim_validation.sh --seconds 120

# 48 小时等效逻辑仿真、每类每种子 1000 次注入
bash tools/run_sim_validation.sh --sim-hours 48 --trials 1000
```

计时窗口最多 300 秒/轮；这不是无人值守的长期监控服务。需要验证更长驻留稳定性时，应另设具有日志轮转、资源监测和退出策略的现场运行任务。

下一层验证仍使用 `tools/verify_ros2_control.sh` 在 Jazzy 中测试实际插件、Action、控制器切换和诊断。实机阶段还需要确认 AL/WKC/DC、CiA402、PDO 周期、实际编码器误差和设备停止行为；本套模拟结果不覆盖这些层。
